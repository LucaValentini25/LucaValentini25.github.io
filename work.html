SOLAR · Performance

From 10 to 200 FPS with a crowd of NPCs on screen

Problem

A living city needs crowds of NPCs, each dressed from the same system as the player. With a standard Animator and skinned mesh per character, a thousand of them dropped the game to ~10 FPS (96 ms/frame) — unplayable, and far worse on a real phone.

Approach

I moved NPC animation and rendering onto the GPU. Animation is baked into a texture at edit time, skinning runs in the shader instead of on the CPU, and the crowd is batched by mesh so the same garment on different characters draws together.

How it works

A custom baker turns each clip into a vertex-animation texture that the shader samples per frame — no Animator, no SkinnedMeshRenderer. A Burst-compiled job feeds the GPU, keeping it off the main thread. The two NPCs in the video are identical to the eye: one on a classic Animator, one fully on the GPU.

Same 1,000-NPC scene: 10 FPS → 215 FPS, and CPU frame time from 96 ms down to 4.7 ms. Zero Animator components, zero skinned meshes.
SOLAR · Game Systems

A character dressing system that had to scale past hand-wiring

Problem

Players build an avatar from garments that come from the backend, get bought in a store, and render on both the player and the NPC crowd — and the catalogue keeps growing. Wiring that by hand as prefabs doesn't survive the second content drop, and the people adding outfits aren't programmers.

Approach

I own this system end to end. Garments are described as data in a node graph rather than assembled by hand, and the team authors them through purpose-built tooling instead of the Inspector.

How it works

A garment graph describes each outfit's parts, slots and colour palettes, kept in sync with the backend catalogue; Addressables keep only what's worn in memory. On top sits an Outfit Editor where a designer composes an outfit, previews it live and saves it back as data. That same data feeds the GPU-skinned NPC crowd — which is why repeated clothing batches across characters.

One system covering authoring, backend sync, the store, the player and the crowd — designers build outfits without touching code.
SOLAR · Architecture

When everything wants to control the camera

Problem

Open world, cutscenes, battles, dressing screens, geolocation — every feature eventually wants to move the camera. Once several systems can each grab it, you get the bug where the camera ends up somewhere nobody intended and no single piece of code is wrong on its own.

Approach

I made camera state single-authority: features declare the context they want, and one arbiter decides — once per frame, in one place.

How it works

Gameplay code never touches a camera; it requests a context. Arbitration happens at a single point in the frame, so resolution order is explicit and debuggable instead of emergent. The deliberate part: the system lives in an assembly that intentionally can't reference Cinemachine — so reaching past the abstraction isn't a code-review note, it's a compile error.

SOLAR · Automation

Internal tooling for the work nobody should do by hand

Problem

A live game accumulates chores: keeping Addressable groups in sync with the folders, regenerating the API client on every backend change, cutting builds with the right keystore and version. Done by hand, each one is a chance to break a build without noticing.

Approach

I built the tools where the chores were — as named editor utilities the whole team uses, not scripts living on my machine.

How it works

An Addressables Folder Manager drives group membership from the folder layout instead of manual assignment. A build-and-API suite regenerates the typed client with backup and rollback, cleans QA state, and handles keystore validation and version injection. A Mesh Instance Baker speeds up scene authoring. Plus smaller quality-of-life tools that remove daily friction.

Waxy · Editor Tooling

Editor tooling that took the busywork out of level building

Problem

Building levels carried a lot of manual busywork: entering Play Mode just to check if a jump was reachable, converting grey blockouts into final prefabs one by one, and typing localization keys clip by clip. None of it was design — it was overhead on top of it.

Approach

Rather than one big editor, I built a small tool for each bottleneck, plus a data-driven tuning pipeline so gameplay values could change without recompiling.

How it works

Replace ProBuilder For Prefab swaps blockout geometry for final prefabs in batch. A Subtitle Localization Helper walks every Timeline and assigns localization keys automatically. And a stats pipeline serializes ScriptableObject values to JSON before each build and re-injects them at runtime — fixing Unity's habit of freezing Play Mode tweaks at build time.

Beyond Unity · External Tooling

Building the tool where the problem actually is

Problem

Not every bottleneck lives inside the engine. Filing a bug meant leaving the conversation where it came up, opening a tracker and re-typing the context — so small issues quietly went unreported.

Approach

If the friction is in Slack, the tool belongs in Slack. I prototyped a bot that turns a message into a tracked ticket without anyone leaving the channel, using a spreadsheet as a lightweight backend.

How it works

A slash command opens a modal — assignee, description, severity — and the bot posts the ticket into a dedicated channel with a follow-up thread and a reassign flow that records who moved it and why. A working prototype, built to prove the workflow.
